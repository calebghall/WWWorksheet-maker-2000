# Roadmap

Goals, in the order the work is sequenced:

1. Tennessee support for kindergarten through Grade 5 is complete (153 standards Supported, 0 Gap, since the three kindergarten and Grade 2 gaps were closed on 2026-11-18). Keep it passing as the modules are regrouped.
2. Let one worksheet hold several configurations of the same module (the "parts" design, called Option B in earlier notes).
3. Add other states' standards.

`notes/standards-coverage.md` stays the source of truth for status. `notes/next-modules.md` describes each proposed module in detail. This file sets the order and the exit criteria.

## Why this order

- No remaining Tennessee row needs several configurations of one module. The one that did (4.NBT.B.5) is handled by the "Also mix in a second size" setting in Multiplication and Division. Parts therefore add nothing to Tennessee completion.
- Parts pay off when another state bundles several skills into one standard. That is a prediction from how some states word their standards, to be checked against real rows from the first non-Tennessee state. Building parts after Tennessee is complete, and before non-Common-Core states, lets the design follow real rows.
- Adding a state is mostly data work once the generator set is complete. Every generator added for Tennessee is also available to other states, so finishing Tennessee first makes each later state cheaper.
- If a second state becomes urgent, swap phases 5 and 6 only after phase 4 is started. Do not start phase 6 before phase 5 has a written design, because the preset format changes in phase 5.

## Phase 0: housekeeping (small)

- Replace hard-coded "Tennessee" strings in the UI and notes with a single framework constant, so phase 6 changes data and not markup. Places today: `src/html/panel-top.html` ("Browse Tennessee Standards"), `src/js/core/standards.js` header comment, `notes/standards-coverage.md` heading text (generated by `tests/coverage.js`).

Exit: tests pass, no user-visible change.

## Phase 5: parts (multiple configurations of one module)

Design, written before code:

- A worksheet is a list of parts. Each part has a module, its own settings and a problem count. Generators already read settings from the state they receive, so a part can run with the state plus that part's settings.
- Combined Worksheet shows parts as lettered sections. Mixed Practice interleaves them at random. A preset chooses which.
- Presets carry a list of parts instead of a single module configuration. `applyStandard` switches to the Combined module and fills the list.
- Editing: a "Save current setup as a part" control captures the current panel settings; parts can be renamed, reordered and deleted. Module panels are not repeated per part.
- The second-size setting in Multiplication and Division (`md.alt`, `md.da2`, `md.db2`) stays until parts cover it, then its preset line moves to two parts.

Constraints:

- Set codes must keep reproducing existing worksheets. Add a test that compares generated sets before and after for fixed seeds across every module.
- Saved settings from earlier versions must load unchanged.

Status: functionally done; release step remains. Done: the parts data model and the set-code regression test (P5.0 to P5.2), Mixed Practice from weighted parts (P5.3), and the panel controls for adding, labeling, resizing, reordering, editing and deleting parts (P5.4). Remaining: review of the design note against real use, and the release tag (P5.6).

Built so far:

- `src/js/core/parts.js`. A part is `{ m, n, label, <settings> }`; the settings key (`as`, `md`, `fd`, `ns`, `tm`, `vis`, `area`, `mix`) and shape match a standards preset, so a single-module preset is a part without a count. `partsOf(st)` returns `st.parts`, or one part per Combined section that is on, so worksheets without parts render exactly as before. The first part of a module keeps the old section seed (`seed|id`); later parts of that module use `seed|id|k`. Parts of one module share a dedupe set so they never print the same problem twice. `clampMod` (moved out of `normalize`) clamps settings for saved parts and saved worksheets alike.
- Presets: `{ c, t, m: 'parts', view: 'combo', parts: [...] }`. `applyStandard` sets `st.parts` and the Combined view and leaves the module tabs alone; a single-module preset clears `st.parts`. 5.NBT.B.7 is now Fractions, Decimals and Percents plus the Number Sense "Decimal division and reasonableness" type, and 4.NBT.B.5 is two Multiplication and Division parts. `md.alt`, `md.da2` and `md.db2` stay in the generator and in `normalize` so saved settings keep their sheets; only the preset moved. This changes the output of those two presets (announced; `tests/golden-sets.json` updated for them only).
- Tests: `tests/logic-setcodes.js` (385 hashed sheets: every module, Combined and Mixed variants, every preset), `tests/logic-parts.js`, part-aware `tests/logic-standards.js` and `tests/coverage.js`, multi-part pages in `tests/clip.py`.
- Mixed Practice: `mixPartsOf` takes the parts that use a mixable topic (parts' `n` are weights, split by largest remainder; equal weights split exactly as topics always were); parts using `vis` or `area` are left out of Mixed. Seeds follow the Combined rule (`seed|mix|id`, then `|k`).
- Panel (`html/parts.html`, `writeParts` and `partAction` in `ui.js`): "Add as a part" on each module tab, and in the Sections list label, size, move, edit, delete (up to 12 parts) and "Use simple sections". Editing loads the part's settings into its tab, which replaces what the tab held; "Update part" writes them back.
- Bug-report links keep `parts` and `combo` when the whole state is too long.

Exit: design note reviewed; a multi-configuration preset works in Combined and Mixed; set-code regression test passes; clipping check covers multi-part pages.

### Why `Area Squares` was separate (and how to combine it)

Mostly **history**, not a hard layout limitation:

- `Area Squares` was the original module, so it kept its own 2-column `.prob` card renderer (`4 / 6 / 8` per page), `Units` dropdown (`units`, `cm²`, `in²`, `ft²`, `m²`), and `Shade the squares` checkbox.
- `Shapes, Measures and Data` (`vis`) came later and uses `CELL_MODS` (`arLayout` / `arithPlan`), which takes `12 / 20 / 30` per page and **automatically steps down to `8`, `6`, or `4` per page** when the SVGs are tall.
- `vis` *already* renders area and 3D-volume SVGs (`acon`, `pera`, `vcubes`, `vlwh`, `vcomp`) inside `CELL_MODS`.

To combine: wrap `count`, `mult`, `draw`, `cmp` and `lsh` as `defTypes` entries inside Geometry using the existing `svg(...)` helper and `win`/`hin` hints. Keep the `Units` dropdown and `Shade the squares` checkbox in that module's panel, active only when a grid-area type is checked. These types then become regular `CELL_MODS` problems and can join `Mixed together`.

### Design rules

1. **Modules follow the standards strands.** Other states reuse the Common Core domains, so strand-named modules keep Phase 6 crosswalks short. Module ids: `addsub`, `muldiv`, `ns` (number and place value), `oa` (operations and algebraic thinking; was proposed as `alg`), `fdp`, `tm`, `meas`, `geom`.
2. **Size cap: about 30 types and 5 groups per module.** `ns` and `fdp` are at the limit. Split a group that grows past about 10 types. In `geom`, Volume and Coordinate plane share one group, "Space and coordinates".
3. **Word problems are a tag, not a group.** Every `defTypes` entry takes `tags: [...]`. Word-style types (`wadd`, `wlen`, `wmul`, `wcmp`, `wstep`, `west`, `mword`, `fword6`, `cstory` and others) carry `tags: ['word']` and live in their home strand. The type search and a "Word problems only" toggle cut across modules. The 7 `ns` word types may stay together as one group in `ns`, but the tag is what filters.
4. **Mapping is keyed by `(oldModule, id)`.** Ids repeat across modules (`cmp` in fdp and in Area Squares, `conv` in fdp and tm). Keys look like `ns.cmp2`, `vis.cmp`, `area.cmp`. A test fails when any registered type has no mapping, or when a mapping names a type that does not exist.
5. **Legacy module ids stay as aliases.** Part and section seeds use the module id (`seed|id`, `seed|id|k`), so moving a type changes its random stream. `ns`, `vis` and `area` stay as hidden legacy modules that old set codes and saved settings load into and render exactly as before. New sheets use the new modules. Presets migrate one at a time. Each preset that changes output is announced and its `tests/golden-sets.json` entry updated, per the working agreements.
6. **Mixability is a property of the group.** Today `area` and `vis` are marked "Sections only" as whole modules. After the move, only specific families (for example solids drawings and large graphs) carry `mix: false`. The Multi-Topic builder shows "Sections only" per family, not per module.
7. **No grade-band filter.** Built in 5.2f, then dropped: the intent was a worksheet covering all standards of a grade, which is now the last entry of the standards list (see 5.2f).
8. **Type counts reconcile before code.** The plan listed about 158 types in 8 modules against 133 registry entries today (65 `ns` and 68 `vis`). 5.2a generates the mapping table from the registry and marks each type moved, merged or new.

## Phase 6: other states

Status (2026-11-18): step 1 is done (Tennessee is a framework: `standards/tn.json`, crosswalk, annotations, per-framework coverage, state picker `#stdFwSel`, content-hashed payload files). Kentucky is the second framework: 149 standards, 138 Supported, 11 Partial, 0 Gap. The three Gap rows shared by both frameworks (`K.CC.C.7`/`KY.K.CC.6`, `K.CC.C.8`/`KY.K.CC.7`, `2.NBT.A.3`/`KY.2.NBT.3`) were closed with three new types: `vis.cmpg` (compare two groups), `ns.cmpw` (compare numerals to 10 in words) and `ns.numrw3` (read and write numbers to 1000), checked by `tests/logic-k2-e.js` and `tests/logic-vis.js`. The type-map cap for `ns` moved from 38 to 41 types. Remaining below: CSP terms and attribution, import validation, size budget, a third framework.

Data source: [Common Standards Project](https://commonstandardsproject.com/developers) (CSP). Its public description: a database of academic standards from all 50 states plus other organizations, grouped into standard sets by jurisdiction, subject and grade or course, with hierarchy, codes and a GUID per standard returned as normalized JSON. The CSP importer builds on Creative Commons licensed standards from the Achievement Standards Network (ASN).

Not yet confirmed (the developer page renders in the browser and could not be read here; check after signing up for a key): the request format and endpoint names, response field names, rate limits, and the terms of use and attribution that apply to the data.

How CSP is used:

- **Import offline, never at runtime.** A script (proposed: `tools/import_standards.py`, next to `tools/make_coin_images.py`) calls the CSP API once per standard set and writes a framework file such as `tests/standards-<framework>.json`. The generated files are committed. The worksheet maker, which is a static GitHub Pages app, never calls CSP.
- **Keep the API key out of the repo and the page.** The script reads the key from an environment variable (a Codespaces secret). A key shipped in the page would be public.
- **Normalize at import.** Each CSP standard becomes a row in the same shape as the Tennessee rows in `tests/standards.json` (grade, cluster, text, code), plus a framework id. Rows keep the CSP GUID so a later re-import updates rows in place.
- **Scope to K-5 math.** Import only the standard sets for mathematics in kindergarten through Grade 5 for each state. Skip course-based sets (high school) until the grade range grows.
- **Validate the import.** A new test checks every imported file for required fields, duplicate codes, empty text, and grade values outside K-5. Imports that fail the test are not committed.

Loading: a state's standards load when that state is picked, not with the page.

- One file per state in the site build (for example `assets/standards/<framework>.json`), fetched the first time the state is chosen in the standards panel and then cached by the browser. This follows the existing pattern for coin images, which the site build loads from files.
- Tennessee is a framework like any other: the same file format, the same crosswalk and the same loader. No code path names Tennessee. The framework a first-time visitor sees is one constant, and Tennessee is only that constant's current value.
- The single-file build (`WWWorksheet-maker-2000.html`) cannot fetch sibling files when opened from disk. Which frameworks it embeds is a build option (a list of framework ids, default `tn`); frameworks not in the list need the site build. If an offline copy with every state is wanted later, pass all of them.
- While a state loads, the panel shows a short loading line. If the fetch fails, it shows a message and keeps the previous state's list.
- File names carry a data version (or a content hash) so a re-import never serves stale cached data.
- Test: a browser test picks a state, checks the list renders from the loaded file, and checks the failure message with the file blocked.

Steps:

1. Move Tennessee onto the framework layout first, as the first framework. Today `tests/standards.json` holds Tennessee only, `src/js/core/standards-all.js` is generated from it, and `src/js/core/standards.js` holds presets keyed by Tennessee code. After the move: rows live in a per-framework file (for example `standards/tn.json`) with a framework id; the presets become the canonical preset set, keyed by canonical id; Tennessee gets a crosswalk file like every other state (mostly identity, since its codes follow Common Core numbering); coverage is generated per framework; and a state picker is added to the standards panel. Tennessee already has verified rows and presets, so it proves the pipeline before any new state. Exit: the rebuilt app and `notes/standards-coverage.md` are unchanged for Tennessee, and the existing tests pass without Tennessee-specific code paths.
2. Keep one set of canonical presets and map each state's codes to them. Many states use Common Core wording, so a crosswalk should cover most rows with no new generator work.
3. Add the second framework: a state whose standards are close to Common Core, to prove the crosswalk and measure how many rows become Gap or Partial. Then take a state with its own wording (for example Texas, Virginia or Florida), where parts are most likely needed.
4. For each new state, generate a coverage note per framework with `tests/coverage.js` and list its Gap rows in the roadmap.
5. Before committing imported text, confirm the CSP terms of use and the license of each state's source data, and add the attribution CSP requires to the app footer and `README.md`. Tennessee's current text came from the Instructional Focus Documents, so its terms are separate.
6. Review imported data per state. CSP text quality varies: codes can be formatted differently from Tennessee's, long standards may be split into sub-bullets, and some states group standards by course rather than grade. Record each state's quirks in its coverage note.

Exit per state: every row in the state's K to 5 standards is Supported, Partial with a note, or an explicit Gap in its coverage note.

## Additional items

Small pieces that the phases above depend on or that are easy to miss:

- **Saved settings and framework id.** The picked standard is stored as a grade and code (`state.std = { g, c }` in `src/js/core/ui.js`). Add a framework id, defaulting to the first-visit constant, and load older saved settings (which have no framework id) as Tennessee. The "Report a problem" link should include the framework and code when a standard is picked.
- **Crosswalk format.** One file per framework mapping each state code to a canonical preset id (or to a Gap or Partial note). Generate per-framework coverage notes with `tests/coverage.js` plus one index note with counts for all frameworks.
- **Provenance metadata.** Each framework file records its CSP standard set id, import date and the data license, so a later re-import can show what changed.
- **Refresh process.** States revise standards on their own schedule. Re-import on demand, and have the import script print a diff (added, removed, changed rows) for review before committing.
- **Size budget.** Set a limit for the built page and for each state file, and make the site-build test fail when either is exceeded.
- **Attribution.** Add the source and license text required for imported standards to the app footer and `README.md`.
- **Scope.** Grades 6 and up, and non-math subjects, are out of scope until the K-5 math frameworks are done. The import filter and framework files should make adding a grade range a data change.
- **Tests per phase.** Import validation (required fields, duplicate codes, grade range), crosswalk completeness (every row mapped or marked Gap), and the load-on-pick browser test.
