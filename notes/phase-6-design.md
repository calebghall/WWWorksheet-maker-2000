# Phase 6 design: frameworks, crosswalks and canonical presets

Status: proposal for review. Written 2026-11-17, after the Tennessee move to `standards/tn.json` (commit following `b53fa5f`).
The roadmap requires this note before Phase 6 work starts.

## 1. What exists

- `standards/<fw>.json`: imported layer, rows keyed by code: `grade, domain, clusterCode, cluster, text, components, guid, asn`, plus `meta` (CSP document title, year, status, source URL, license, import date). Built by `tools/import_standards.py` and `tools/build_framework.py`.
- `standards/<fw>.annotations.json`: hand-kept layer (examples, NOTE text, table references), keyed by code with the GUID. Never overwritten by an import.
- `src/js/core/standards.js`: 150 presets keyed by Tennessee code (`c`), against 153 Tennessee rows in `tn.json`. The 3 rows without a preset (`K.CC.C.7`, `K.CC.C.8`, `2.NBT.A.3`) are Gap rows and stay Gap. A preset configures one module, or several parts (`m: 'parts'`).
- `FRAMEWORK` (framework.js): one constant for the framework a first-time visitor sees.

## 2. Decisions

1. **Canonical preset ids are neutral recipe ids, not any state's code** (decided 2026-11-17). An id names a worksheet recipe, so several standards from several frameworks can point at it, and a recipe can be split or merged without touching a state's code. Format: `<strand>.<skill-slug>`, for example `frac.equiv-visual`. Ids are never renamed; a replaced id stays as an alias. Tennessee then has a real crosswalk table (153 rows: 150 generated once from the current presets and reviewed, plus the 3 Gap rows) instead of identity. `state.std.c` keeps holding the picked framework's own code. The worksheet title prints the picked framework's code, not the canonical id. Mechanical migration, one patch before the loader: rename `c` to `id` in `standards.js` (slugs proposed from preset titles), generate `tn.crosswalk.json`, rename the 300 `std|<code>|<seed>` keys in `tests/golden-sets.json` keeping the hash values, and switch the 15 `STD_BY_CODE` / `std.c` references in `src/js/core` to resolve through the crosswalk. Exit: all existing golden hashes identical.
2. **One crosswalk file per framework**, `standards/<fw>.crosswalk.json`:
   ```json
   { "framework": "ky",
     "rows": {
       "KY.5.NF.1": { "to": ["5.NF.A.1", "5.NF.A.2"], "status": "supported" },
       "KY.5.MD.2": { "status": "gap", "need": "statistical questions and data collection" },
       "KY.4.G.3":  { "to": ["4.G.A.3"], "status": "partial", "note": "symmetry by folding only" } } }
   ```
   - `to`: canonical preset ids. One id builds that preset. Several ids build a Combined worksheet with one part per id (the existing parts mechanism; a target that is itself a parts preset is flattened).
   - `status`: `supported`, `partial` (note required) or `gap` (`need` required, no `to`). The effective status is the worst of the declared status and the statuses of the target presets.
   - `need` is a short capability phrase. Gap lists from all frameworks are grouped by it, which turns state differences into a generator work list.
3. **Tennessee gets an identity crosswalk**, generated by a script and checked by a test. The 3 unmapped rows are `status: gap` with a `need` (`K.CC.C.7`, `K.CC.C.8`: compare groups and numerals as greater than, less than or equal; `2.NBT.A.3`: read and write numbers in standard, word and expanded form). A standard without a generator is a Gap; no preset is invented for it. No code path names Tennessee.
4. **Crosswalks are hand-reviewed, with generated proposals.** A script proposes `to` for each row from cluster text and text similarity (about 30 of 149 Kentucky rows match at 0.85 or higher), and a person confirms every row. Similarity is never applied silently, because states regroup standards.
5. **Annotations stay authoring aids.** They are not loaded by the app. `tests/coverage.js` prints a standard's annotation under every Partial or Gap row in the coverage note, so the person judging coverage sees the examples.
6. **Saved settings:** `state.std = { f, g, c }`. The app is in testing only, so no migration or backward compatibility is kept for earlier saved settings: settings without `f` fall back to the default framework and an unknown `c` is cleared. "Report a problem" includes `f` and `c`. Set codes (the seed) are unchanged.
7. **Loading:** as in the roadmap. One file per framework, fetched on first pick, cache-busted by a content hash in the file name. The single-file build embeds a configurable list of ids, default `tn`. The picker list (`STD_ALL`) is generated per framework from the imported layer.
8. **Coverage per framework:** `tests/coverage.js` loops over `standards/*.json` and writes `notes/coverage/<fw>.md` plus `notes/standards-coverage.md` as the index (counts for all frameworks).

## 3. Tests

- `tests/logic-frameworks.js`: required fields, unique codes and GUIDs, grade in K-5, text present, annotation keys exist in the framework.
- Crosswalk completeness: every row has an entry; every `to` id exists in `STD_BY_CODE`; `gap` rows have `need`; `partial` rows have `note`; Tennessee is identity.
- Preset check (existing `logic-standards.js`) runs for every crosswalk target, including multi-target Combined builds.
- Browser test: pick a framework, list renders from the loaded file, failure message with the file blocked.
- Golden hashes for existing Tennessee set codes must not change.

## 4. Order of work

1. Loader, framework picker, `state.std.f`, per-framework coverage (Tennessee only; no visible change).
2. `ky.json` crosswalk, hand-reviewed from generated proposals; Kentucky coverage note and gap list.
3. Generator work for Kentucky gaps, grouped by `need`.
4. Third framework with its own wording (Texas, Virginia or Florida).
5. Tennessee reuse terms confirmed with the Tennessee State Board of Education.

## 5. Decisions made (2026-11-17)

- Canonical ids are neutral (section 2.1).
- Multi-target rows build a Combined worksheet (section 2.2).
- Kentucky is the second framework.
- Attribution: Kentucky standards are public record. The CC BY 3.0 US attribution applies only to the Common Standards Project JSON format, so it is kept as comments in the importer and framework-build code, with no footer or README entry.
- No backward compatibility for saved settings (testing only).
- Standards without a generator are Gap rows; none are added or approximated to fill them.

## 6. Open: settings from a code

Today the set code (`seed`, six characters) fixes only the random stream. Settings are not in it. Proposed, separate from the seed so existing codes and footers are untouched:
- A share code `v1.<base64url(deflate(JSON))>` holding the settings that differ from defaults plus the seed. Where a framework standard is picked, it holds `{ f, c, level, seed }` plus a preset version, so it stays short; otherwise it holds the full diff.
- Accepted in the existing set-code box (`v1.` prefix, larger `maxlength`) and offered as a copyable link `#s=...` and a QR code. Static page, no server.
- Unknown ids on decode (removed types) are skipped with a message. A preset version mismatch shows a warning.
- Tests: round trip for every golden configuration; old six-character codes still load.
